# Postcard Migration

Everything about migrating legacy Strapi `postcards` into the new
`postcards` table, including **tags → `facet_assignments`**
(`owned_type='postcard'`) via the Experience facet (tracker row **#16**).
Executed by `scripts/postcard.py` (step 8 of `scripts/migrate_data.py`); the
same logic lives in `notebooks/postcard_migration.ipynb` for interactive
runs, which also carries the optional author-circles step (notebook only).

!!! note "`postcards` has two sources"
    Since 2026-08-11 the `postcards` table is written by **two** migrations:
    `scripts/directory_album.py` puts Restaurants/Events/Shopping **albums**
    there (they have no Collection layer — see
    [Directory & Album migration](directory-album-migration.md#the-album-split-collections-vs-postcards)),
    and this step adds the legacy **postcards**. The two never collide:
    album-derived slugs are reserved before this step generates any.

## Dependencies — why this runs last

A postcard consumes the per-environment map files produced by earlier
steps (suffix from the DB name in `DATABASE_URL`):

- `legacy_album_id_map_*.json` (directory/album migration) —
  `postcard.album` → `collection_id`, and `collection_type_id` is copied
  from that collection row.
- `legacy_album_postcard_id_map_*.json` (directory/album migration) — albums
  that became postcards instead of collections. A legacy postcard under such
  an album gets `collection_id = NULL` and inherits `collection_type_id` +
  geo from the album-derived postcard. Optional: an absent file is treated as
  empty, so older runs still work.
- `legacy_tag_id_map_*.json` (tags facet migration) — each `postcard.tags[]`
  entry → a `facet_assignments` row pointing at its Experience facet_value.
  The tags migration created the vocabulary; this step creates the actual
  attachments that make the facet queryable.

## Field mapping — Postcard

Legacy `api::postcard.postcard` → new `postcards`.

| Legacy field | Type | New column | Notes |
|---|---|---|---|
| `name` | string | `name` | trimmed; postcards without a name are skipped → printed list |
| `intro` / `story` | text | `intro` / `story` | trimmed; empty → NULL |
| `slug` | string | `slug` (unique) | majority empty in legacy → generated by slugify(name); all slugs de-duplicated in-run (`foo`, `foo-2`, ...) — id-sorted so suffixes stay stable across re-runs. Slugs owned by album-derived postcards are reserved first, so this step never upserts over one |
| `album` | relation | `collection_id` (FK) + `collection_type_id` (FK) | via the album id maps — see the table below |
| `country` | relation | `country_id` (FK) | matched by name (how geo migrated); falls back to the parent's country; misses printed for review |
| — | | `region_id` / `locality_id` | inherited from the parent **only when** the parent's country matches the resolved country; `city_id` stays NULL |
| `coverImage` | media | `cover_media_id` (FK → `media`) | find-or-create by normalized url (reuses `media.py` rows, never duplicates) |
| `copyright` | string | `copyright` | trimmed; empty → NULL |
| `isFeatured` | boolean | `is_featured` | |
| `priority` | int | `priority` | NULL → 0 |
| `isComplete` | boolean | `status` | legacy has no status enum — `true` → `live`, else `draft` |
| `createdAt` | timestamp | `published_at` | **only for live postcards** — the one timestamp carried over |
| `tags` | manyToMany | `facet_assignments` rows | `(owned_type='postcard', owned_id, facet_value_id)` via the tag id map; merged duplicate tags converge on the same value, the unique key absorbs repeats |
| `user` | relation | Circle `author` | **notebook-only optional step** (needs the per-env legacy user id map) |
| `articleURL` | string | — | **dropped** — empty everywhere (reviewed 2026-08-07) |
| `isFounderStory` | boolean | — | **dropped — no v2 home**; revisit if it should become a facet or flag |
| `album_themes` | relation | — | empty on postcards; themes live on albums → facet migrations |
| `bookmarks` | relation | — | migrated by the [Bookmark migration](bookmark-migration.md) (tracker #18, Circle bookmark) |
| `memories` | relation | — | deferred → tracker #19 (Memory) |
| `property_itineraries` | relation | — | migrated by the [Journey migration](journey-migration.md) (tracker #31) |
| `createdAt/updatedAt`, `createdBy/updatedBy` | Strapi housekeeping | — | dropped (except `published_at` above) |

`location`, `event_details` and `website` stay NULL for legacy postcards —
they carry no coordinates, event data or site link. (Album-derived postcards
*do* populate those three; this step's `ON CONFLICT` clause leaves them
untouched.)

### How `album` resolves

| The postcard's album… | `collection_id` | `collection_type_id` | geo inherited from |
|---|---|---|---|
| became a **collection** (Properties) | that collection | copied from it | that collection |
| became a **postcard** (Restaurants/Events/Shopping) | **NULL** | copied from the album-derived postcard | that postcard |
| is **Designer Tours** (in neither map) | — **skipped** → dx-card migration (#11/#13) | | |
| is **missing** (no album at all) | NULL | Properties (default) | — |

Row 2 is 0 postcards in prod and 6 in dev, all printed under
`album is itself a postcard`.

### Design decision — `collection_id` kept where a collection exists

The schema convention says `collection_id` is populated only for
dedicated-collection types (Properties / Destination Expert). For postcards
whose album *is* a Properties collection the migration keeps the FK **and**
sets geo directly — dropping the linkage would destroy data irreversibly,
while nulling it later is a one-line UPDATE. For the non-dedicated types the
FK is genuinely NULL now, because no Collection row exists to point at.

## Output artifact — legacy postcard id map

The script writes `legacy_postcard_id_map_dev.json` / `_prod.json` (legacy
postcard id → new id) to the repo root — the bookmarks (#18) and memories
(#19) migrations need it. Suffix picked automatically from the DB name in
`DATABASE_URL`.

## Idempotency

Postcards upsert on `slug`; facet assignments insert with
`ON CONFLICT (owned_type, owned_id, facet_value_id) DO NOTHING`; cover media
rows are found-or-created by url. Safe to re-run.

## What needs manual work — checklist

1. **Skipped postcards** — the printed Designer Tours list is expected (they
   migrate with dx-cards); anything else in the skip lists needs a look.
2. **Country misses** — postcards whose country name found no `countries`
   row keep the collection fallback or NULL; review the printed list.
3. **Unmapped tags** — legacy tags missing from the tag id map mean the tags
   facet migration is stale; re-run it and then re-run this step.
4. **`isFounderStory`** — dropped; decide whether it should become a facet
   value or a flag before the legacy CMS goes away.
5. **Author circles** — run notebook section 6 when circle work unblocks.
6. **Deferred work** — bookmarks, memories and property itineraries have
   their own tracker rows and consume the postcard id map.

## Verification

The script ends with a per-type breakdown (total / with a collection /
without one), totals (cover / country / live), facet-assignment counts and a
duplicate-slug check — compare against the source CMS counts for the
environment being migrated.

Two invariants worth checking after both steps have run:

- `bad: nonded w/ coll` must be **0** — no postcard of a non-dedicated type
  may carry a `collection_id`.
- Restaurants/Events/Shopping totals should equal the album-derived counts
  (341 / 91 / 235 in prod) plus any legacy postcards under those albums (0 in
  prod).

## Run order

```text
... → scripts/directory_album.py → scripts/tags_facet.py → scripts/postcard.py
```

Must run **after** the directory/album and tags facet migrations (the album
collection map and the tag map are hard prerequisites — it fails fast if
either is missing; the album→postcard map is optional) and **before**
bookmarks/memories. Or just run `python scripts/migrate_data.py`,
which sequences everything and stops on the first failure.
